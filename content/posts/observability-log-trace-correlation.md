## 문제 — 수집은 다 되는데 서로를 못 찾는다

3-pillar(메트릭·로그·트레이스)가 전부 떠 있었고 대시보드도 정상이었습니다. 그런데 장애 조사 시 **"이 트레이스의 로그"** 로 점프가 안 됐습니다.

```text
[Tempo에서 trace ID 복사] → [Loki에서 검색] → 0건
```

backend도, fastapi도 마찬가지였습니다. 같은 요청을 가리키면서 두 신호가 서로를 찾지 못하는 상태였습니다.

## 왜 이게 중요한가 — 개별 신호의 가치는 상관에서 나온다

관측을 세 신호로 나눠 수집하는 이유는 각각의 강점이 다르기 때문입니다. 메트릭은 추세를, 로그는 이유를, 트레이스는 경로를 보여줍니다.

문제가 나면 세 신호를 오갑니다. **알림(메트릭) → 트레이스로 병목 지점 확인 → 그 순간의 로그로 원인 확인.** 이 흐름이 끊기면 신호를 각각 아무리 잘 모아도, 원인 분석은 여전히 눈대중이 됩니다.

그래서 이 문제의 목표는 **로그와 트레이스를 하나의 요청 컨텍스트 안에서 연결하는 것** 이었습니다.

## 상관의 계약 — 로그 라인 안에 trace_id를 넣는다

Loki와 Tempo를 잇는 표준 방법은 **로그 라인 안에 trace_id를 심고, Loki의 `derivedFields`가 그 값을 추출해 Tempo 링크로 변환**하는 것입니다.

```text
[로그]  2026-07-23 14:22:11 INFO  trace_id:21d9800f...bda9e  GET /guide 200
                                  └────────────┬───────────┘
                                  Loki derivedFields regex 가 추출 → Tempo 링크
```

즉 이 상관에는 **세 주체가 관여**합니다.

1. **애플리케이션** — 로그 라인에 trace_id를 실제로 찍어야 합니다
2. **Loki** — 로그에서 그 값을 추출하는 regex(`derivedFields`)를 정확히 알아야 합니다
3. **Tempo** — 추출된 값을 받아 해당 trace를 조회할 수 있어야 합니다

셋 중 하나라도 계약이 어긋나면 상관이 조용히 깨집니다. 그리고 **깨졌다는 신호가 UI에 뜨지 않습니다** — 그저 검색 결과가 0건일 뿐입니다.

## 가설을 세 번 벗겨냈다

수집은 정상이고 대시보드도 뜨는데 상관만 안 된다면, 어디가 끊긴 걸까요. 원인의 후보가 여러 곳이라 가설을 순서대로 벗겨봤습니다.

### ① 경로 — Alloy 배선이 잘못됐나

첫 의심은 수집기 배선이었습니다. Alloy가 로그를 Loki로 보낼 때 필드를 잘 넘기고 있는지 확인했습니다. **완비돼 있었습니다.** 로그도 정상 도착 중이고, `derivedFields` 설정도 Grafana에 등록돼 있었습니다.

경로는 문제가 아니었습니다.

### ② 필드 — env로 MDC 캡처를 지시하면 되지 않나

두 번째로 의심한 건 필드 캡처였습니다. OpenTelemetry Java Agent는 MDC(Mapped Diagnostic Context)에 `trace_id`를 자동으로 넣어줍니다. 그러니 로거가 MDC를 찍도록 설정하면 되지 않을까 — env 변수로 시도했습니다.

**무효했습니다.** 그리고 이 지점에서 중요한 것 하나를 알게 됐습니다.

> **appender 부재는 env 튜닝으로 못 채운다.**
> 속성을 붙일 주체(로그 appender)가 없는데 *"캡처하라"* 는 지시는 무의미합니다.

이 교훈은 나중에 FastAPI 쪽에서 또 한 번 반복됩니다.

### ③ 패턴 — 그럼 어디에서 끊긴 걸까

세 번째로, `%X{trace_id}`를 로그 패턴에 임시로 주입해봤습니다. stdout에 **32-hex** 문자열이 그대로 찍혔습니다.

즉 **MDC엔 이미 trace_id가 있었고, 로그 패턴이 안 찍고 있었을 뿐**이었습니다. OTel Agent는 정상 동작 중이었고, Spring 콘솔 로그 패턴에서 `%X` 지시자가 빠져 있었던 게 원인이었습니다.

한 발 더 있었습니다. Loki `derivedFields`의 regex는 `trace_id[":\s]+`로 되어 있어서 **`trace_id: 값` 은 매치되지만 `trace_id= 값` 은 매치되지 않습니다.** 로그 패턴을 고칠 때 구분자를 `:`로 정확히 맞춰야 계약이 성립했습니다.

> **로그 포맷과 파서 regex는 별개 설정이 아니라 하나의 계약입니다.** 한쪽만 고치면 조용히 깨집니다.

## FastAPI에서 마주친 다른 층 — 설정이 prod에서 무효

같은 계약을 FastAPI에도 적용하려 했는데, 여기서는 **env 기반 로그 포맷 지정 자체가 prod에서 no-op** 이었습니다.

원인은 uvicorn이었습니다. uvicorn이 애플리케이션보다 먼저 로거를 잡아서, 앱에서 지정하는 로그 포맷이 uvicorn의 기본 포맷에 **덮이는 구조**였습니다. env로 준 설정은 이미 잡혀 있는 로거 앞에서 무력했습니다.

커밋 직전 로컬 검증에서 이걸 잡았습니다. env가 아니라 코드에서 `logging.basicConfig(force=True)`로 root logger를 명시적으로 재설정하는 방식으로 전환했습니다. **prod 조건 차이를 커밋 전에 잡을 수 있었다**는 게 검증 순서의 값어치였습니다.

## 실측으로 확정 — 40요청 → 100% 도달 → 교집합 3

계약을 다 맞춘 뒤 실제로 동작하는지 재봤습니다.

```text
40요청 발생
  → stdout에서 고유 trace_id 48개 확인 (여러 로그 라인에서 반복)
  → Loki 도달률 100% (로그는 무샘플링)
  → Tempo 교집합 3
```

**교집합 3은 결함이 아니라 정합의 증거입니다.**

트레이스는 성능 이유로 샘플링을 겁니다. 이 프로젝트는 트레이스 샘플러가 대략 10%로 잡혀 있었고, 40요청이면 확률상 **3~4개**가 남습니다. 3이 나온 게 오히려 "샘플러가 정직하게 동작 중"이라는 뜻입니다.

만약 여기서 40에 가까운 값이 나왔다면 그게 오히려 문제였을 겁니다 — 샘플링이 안 걸린다는 뜻이거나, 검증 방법이 잘못됐다는 뜻이거든요.

### 검증할 때 놓치기 쉬운 것 — 배치가 대칭이어야 한다

이런 검증에서 제일 조용히 망가지는 것이 **로그만 내는 요청과 트레이스만 내는 요청을 섞는 경우**입니다.

예를 들어 헬스체크는 로그는 남기지만 스팬을 안 만들 수 있고, 반대로 어떤 내부 호출은 스팬만 만들고 로그가 없을 수 있습니다. 이런 요청을 섞어서 재면 교집합이 인위적으로 낮아져 **"상관이 안 된다"고 오판**합니다.

동일한 요청 하나로 로그와 트레이스가 함께 생성되는 시나리오만 골라서 검증해야 합니다.

## 후일담 — 계약은 맞췄는데 앱이 그 통로를 안 쓴다

며칠 뒤 FastAPI 쪽 점프 캡처를 뜨려고 Loki를 뒤졌더니 이상한 게 있었습니다.

```text
$ kubectl logs -n drawe-prod -l app=fastapi-guide --since=1h | grep -c "trace_id:"
0
```

**0건.** 계약은 맞췄는데 왜 안 나올까 하고 실제 로그 본문을 봤더니 답이 있었습니다.

```text
{"body":"[llm] grok finish=stop clen=520 reasoning=1506"}          ← 형식이 없음
{"body":"INFO:     10.10.x.x - \"GET /health HTTP/1.1\" 200 OK"} ← uvicorn 자체 형식
```

지정한 `trace_id:%(otelTraceID)s` 형식을 따르는 로그가 하나도 없었습니다.

코드를 세어보고서야 원인이 명확해졌습니다.

| 서비스 | `print()` | `logger.*` |
| --- | --: | --: |
| fastapi-guide | **157** | **0** |
| fastapi-embed | **256** | 2 |

`app.py`에 `log = logging.getLogger(...)`로 로거를 만들어 뒀지만, **파이프라인 코드는 그 로거를 쓰지 않았습니다.**

`print()`는 파이썬 표준 logging을 거치지 않고 stdout으로 직행합니다. root logger 포맷을 아무리 정확히 고쳐도 `print()`가 뿌리는 로그에는 아무 영향을 못 줍니다. 계약은 정확했는데 **적용 대상이 되는 로그가 사실상 warmup 한 줄뿐** 이었던 겁니다.

### 끊긴 지점이 한 칸 앞으로 옮겨졌다

원래 정리한 파이프라인은 이랬습니다.

```text
① trace context 생성 (OTel)        ✓
② 포맷이 trace_id 출력              ✗ ← 원래 여기가 끊긴다고 봤다
③ regex 가 추출                     ...
```

그런데 실제로는 한 칸이 더 있었습니다.

```text
① trace context 생성 (OTel)        ✓
② logging 모듈 경유                 ✗ ← print() 라 여기서 끊긴다
③ 포맷이 trace_id 출력              (도달 못 함)
④ regex 가 추출                     (도달 못 함)
```

backend(Java)는 프레임워크가 로깅을 강제하니 ②가 자연히 성립합니다. Python은 `print()`로도 로그가 "보이기" 때문에 ②를 건너뛰고도 개발이 굴러갑니다. 그래서 **계약을 맞춰도 절반만 이어졌던** 겁니다.

다만 트레이스 자체는 온전했습니다. `print()`는 stdout에만 쓰는 것이라 스팬 생성과 무관하거든요. `guide.coach`가 60초 걸린 병목은 Tempo에서 그대로 보였습니다. **잃은 것은 "그 요청의 로그를 찾아가는 길"** 이었고, 그 순간 LLM이 무엇을 반환했는지(`[llm] grok finish=stop clen=520`)를 찾으려면 타임스탬프로 눈대중을 해야 했습니다.

## 조치 — 헤드라인 숫자부터 검증했다

`print()`를 `logger` 호출로 옮기기로 했는데, 착수 전에 **범위 조사부터** 했습니다. 157개, 256개라는 헤드라인 숫자가 실제 전환 대상 수와 다를 수 있어서요.

| | 전체 `print()` | 제외(도구·평가·스크립트·CLI) | **실제 전환 대상** |
| --- | --: | --: | --: |
| fastapi-guide | 157 | 97 | **60** |
| fastapi-embed | 256 | 253 | **3** |
| **합계** | 413 | | **63** |

embed의 256곳 중 253곳은 `scripts/` (일회성 인덱싱·재구성 도구)였습니다. 요청 컨텍스트 밖에서 도는 배치라 로거로 옮겨도 `trace_id: 0`만 찍힙니다.

> **"157곳을 고쳐야 한다"는 전제부터 검증해야 했습니다.** 조사만으로도 작업 범위가 60개로 줄었습니다.

전환 자체는 기계적이었지만, 두 가지가 함께 붙어 있었습니다. **로거 이름**을 `drawe-fastapi.guide.<module.path>` 로 붙였는데, `app.py`가 `setLevel(INFO)`하는 네임스페이스 하위여야 실제로 출력됩니다 — 한 글자만 틀리면 조용히 안 찍힙니다. 그리고 **로컬 관측 스택**을 열어보니 `docker-compose.observability.yml`에 `OTEL_PYTHON_LOG_FORMAT`이 없었고 `guide` 서비스 블록 자체가 빠져 있었습니다. 로컬에서 재현할 수 없는 상태였다는 뜻이라, 같은 PR에서 ConfigMap과 byte-identical하게 정합을 맞췄습니다.

## 배포하고 확인 — 대조 실측으로 증명

동일한 `/guide` 요청(Grok 실호출 포함, 둘 다 200)으로 코드 변수만 격리해 비교했습니다.

| | `trace_id:` 문자열 | **32hex(요청 컨텍스트)** |
| --- | --: | --: |
| BEFORE (`print`) | 2 | **0** |
| AFTER (`logger`) | 8 | **5** |

BEFORE에서 `trace_id:`가 2건 잡힌 건 이미 logger를 쓰던 warmup 로그였습니다. 판정 기준인 32hex는 정확히 0 → 5 로 갈렸습니다. prod 배포 후에도 같은 수치가 재현됐고, Grafana에서 FastAPI 로그의 `trace_id`를 눌러 Tempo로 점프하는 것도 확인했습니다.

![로그의 trace_id 링크를 누르면 Tempo 로 이동한다](/images/posts/observability-loki-trace-jump.png)

점프한 트레이스에서는 backend 자동 계측과 guide 수동 계측이 한 계층으로 이어져 보였고, `guide.coach`가 전체 1분 18초 중 **50.3초(64%)** 를 쓰는 병목도 그대로 읽혔습니다. 이제 그 순간의 로그도 함께 볼 수 있게 됐습니다.

## 배운 점

1. **관측의 가치는 개별 신호가 아니라 신호 사이의 연결에서 나온다.** 잘 모으는 것과 잘 잇는 것은 다른 문제다.
2. **로그 포맷과 파서 regex는 하나의 계약이다.** 구분자 하나만 어긋나도 상관이 조용히 깨진다.
3. **appender 부재는 env 튜닝으로 못 채운다.** 속성을 붙일 주체가 없는데 캡처하라는 지시는 무의미하다.
4. **설정을 고치기 전에 그 통로를 앱이 실제로 쓰는지 세어봐야 한다.** `print()` 157개 앞에서 로거 설정은 무력하다.
5. **헤드라인 숫자부터 검증한다.** "157곳"이 실제로는 60곳이고 "256곳"이 3곳이었다. 범위 조사 자체가 작업의 절반이다.
6. **검증 배치는 대칭이어야 한다.** 로그만 내는 요청과 트레이스만 내는 요청을 섞으면 교집합이 인위적으로 낮아져 오판이 난다.
