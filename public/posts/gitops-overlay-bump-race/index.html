GitOps에서 git은 데이터베이스다 — 동시 배포 경합과 브랜치 드리프트 막기

여러 서비스의 CD가 같은 브랜치에 동시에 push하다 실패했다. 그리고 환경을 브랜치로 나눈 구조에선 승격이 운영 이미지를 과거로 되돌릴 수 있었다. 복구 자동화와 사전 차단, 두 층으로 막은 기록.

배경 — CI가 클러스터 대신 git을 만진다

GitOps로 옮기면서 CI의 역할이 바뀌었습니다. 예전엔 CI가 클러스터를 직접 갱신했지만, 이제는 이미지를 만들고 오버레이의 이미지 태그를 git에 커밋하는 것까지만 합니다. 클러스터 반영은 ArgoCD가 git을 보고 알아서 하고요.

그런데 이 구조는 git을 배포 상태의 데이터베이스로 쓴다는 뜻이기도 합니다. 그러면 데이터베이스에서 겪는 문제가 그대로 따라옵니다 — 동시성과 복제 일관성.

문제 ① 동시 배포가 서로를 밀어낸다

모노레포라 여러 서비스가 한 커밋으로 함께 배포되는 일이 잦았습니다. 그러면 각 서비스의 CD가 동시에 실행되어 같은 브랜치에 push를 시도합니다.

먼저 push한 쪽이 성공하면, 나중 쪽은 자기가 알던 커밋이 더 이상 브랜치 끝이 아니라서 non-fast-forward로 거절됩니다. 배포가 코드 문제도 인프라 문제도 아닌 경합 때문에 실패하는 거죠. 그때마다 사람이 들어가 다시 돌려야 했습니다.

해결 — 파이프라인이 스스로 복구하게

push 단계를 이렇게 바꿨습니다.

push 실패
  → 작업트리 정리
  → rebase 가 이미 진행 중인지 가드
  → fetch
  → rebase (남의 커밋 위로 내 태그 변경을 얹음)
  → 재push

핵심은 rebase입니다. 내 변경은 “오버레이 태그 한 줄"이라 남의 커밋 위에 얹어도 충돌이 없거든요. “이미 rebase 중인지” 가드를 둔 건, 재시도가 겹칠 때 파이프라인이 어중간한 상태에 갇히는 걸 막기 위해서였습니다.

사람이 개입하던 실패가 파이프라인의 자가 치유로 바뀌었습니다.

문제 ② 승격이 운영을 과거로 되돌린다

더 위험한 건 두 번째였습니다. 환경을 브랜치로 나눈 구조(dev=develop, prod=main)에선 prod 오버레이 파일이 두 브랜치에 복제됩니다.

여기서 사고 시나리오가 생깁니다.

main   : prod 오버레이 = 최신 태그   (운영 중)
develop: prod 오버레이 = 옛 태그     (복제본이 낡음)

develop → main 승격 머지
  → main 의 prod 오버레이가 옛 태그로 덮임
  → ArgoCD 가 git 을 진실로 여기고 수렴
  → 운영이 과거 이미지로 롤백

배포가 앞으로 가야 하는데 뒤로 가는 겁니다. 그것도 아무도 “롤백하자"고 하지 않았는데요. 복제본이 있는 한, 복제본이 낡는 건 시간 문제입니다.

해결 — 두 층으로 막았다

1층: 평시 자동 동기화. main에서 prod 오버레이를 bump할 때 develop의 사본도 같은 태그로 맞춥니다. 복제본이 애초에 낡지 않게 하는 거죠. 이때 prod 오버레이만 건드려서 dev 배포에는 영향이 없게 했습니다.

2층: 승격 시점 게이트. 그래도 낡을 수 있으니, main 대상 PR이 prod 오버레이를 바꾸는지 검사하는 워크플로를 뒀습니다. 드리프트가 있으면 승격 단계에서 잡힙니다.

게이트는 diff가 아니라 ‘머지 결과’를 본다

이 게이트에서 가장 중요한 결정이 이거였습니다.

PR의 diff를 보는 건 부정확합니다. diff는 병합이 자동으로 해소되기 전의 모습이라, 실제로 머지하면 어떻게 될지와 다를 수 있거든요. 그래서 게이트는 PR을 실제로 머지했을 때의 트리를 검사합니다.

게이트는 변경 의도가 아니라 머지 이후의 실제 운영 상태를 검사한다.

정상 케이스(3-way 병합이 main 값을 유지하는 경우)는 “같음"으로 통과해서 오탐이 없습니다. 오탐이 나는 게이트는 결국 무시당하니, 이 부분이 게이트를 신뢰할 수 있게 만든 지점이었습니다.

배운 점

  1. GitOps에서 git은 데이터베이스다. 동시성(경합)과 복제 일관성(드리프트) 문제가 그대로 옮겨온다 — 브랜치 전략을 짤 때 이걸 염두에 둬야 한다.
  2. 방어는 두 층으로. 복구 자동화(rebase 재시도)만으로도, 사전 차단(게이트)만으로도 부족하다. 평시에 어긋나지 않게 하고, 그래도 어긋나면 승격에서 잡는다.
  3. 검사는 “그럴 것 같다"가 아니라 “이렇게 된다"를 봐야 한다. diff가 아니라 머지 결과를 검사한 이유이고, 오탐 0이 게이트의 신뢰를 만든다.
