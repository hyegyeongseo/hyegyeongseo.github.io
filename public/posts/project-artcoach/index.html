artcoach — 검색만 있던 제품에 에이전트를 만들어 넣기까지 (개인 프로젝트)

'창작 지원 AI 에이전트'를 표방했지만 실제로 동작하는 건 레퍼런스 검색뿐이었습니다. 관찰→진단→행동 제시를 하는 에이전트를 개인 프로젝트로 만들어 검증하고, 팀 프로젝트 DraWe에 도입해 한 끗 가이드와 완성작 갤러리가 됐습니다.

제가 만든 것

  • 한 끗 가이드 — 분석 → 한 끗 포인트 → 추천 레퍼런스 → 다음 단계 → 성장 흐름 골격
  • 성장 상태머신 — 목표 유지 · 반복 패턴 추적 · 단계 진행 판정을 LLM 없이 결정적으로
  • 진단 엔진 — taxonomy 14축, 기하/명도/색 신호, track별 측정 norm 분기
  • 가드레일 — 스키마 · 닫힌 세계 · 금지 표현 · 근거 4중 검증
  • 레퍼런스 코퍼스 — 상업 사용 가능 자료만, QC 게이트, 피드백 리랭크
  • 평가 harness — safety · retrieval · diagnosis 회귀 + 명암 축 채점

“AI 에이전트"라고 했는데 검색만 있었다

팀 프로젝트 DraWe의 주제는 창작 지원 AI 에이전트였습니다. 그런데 그 시점에 실제로 동작하던 건 레퍼런스 추천 — 검색이었습니다. 원하는 무드의 참고 이미지를 찾아 보드에 모으는 것. 에이전트라고 부를 만한 게 아직 없었습니다.

검색은 사용자가 무엇을 찾아야 하는지 알 때 동작합니다. 그런데 그림 앞에서 막힌 사람은 그걸 모릅니다. “이런 그림들을 참고하세요"는 참고물이지 해답이 아니고, 100장을 줘도 무엇을 왜 봐야 하는지 모르면 그대로 멈춰 있습니다.

그래서 관찰하고 → 판단하고 → 다음 행동을 제시하는 쪽을 만들어봤습니다. 찾아주는 게 아니라 짚어주는 쪽으로.

그리고 궁금한 게 있었다

제품 쪽 이유만은 아니었습니다. 에이전트 워크플로를 직접 설계해보고, 그 구조가 인프라 요구사항을 어떻게 바꾸는지 확인하고 싶었습니다.

클라우드 구성은 리소스를 고르는 일이 아니라 서비스가 어떻게 동작하는지에서 따라 나온다고 생각했는데, 그러려면 서비스 쪽을 내가 알아야 하니까요. 에이전트 워크로드는 CRUD API와 다릅니다 — 요청 하나가 초 단위로 길고, 외부 모델·벡터 스토어·오브젝트 스토리지를 차례로 오가서 실패할 수 있는 지점이 흩어져 있고, 비용이 요청 수가 아니라 토큰·이미지 수에 붙습니다. 그 차이가 스케일링·추적·비용 관측으로 어떻게 이어지는지 직접 겪어보고 싶었습니다.

팀 코드베이스가 아니라 따로 둔 건 “안 되니까 접자"는 결론을 내기 쉽기 때문입니다. 일주일 동안 “진단이 근거를 갖는가"와 “성장이 누적되는가” 에만 시간을 썼습니다.

무엇이 DraWe로 갔나

검색만 있던 제품에 에이전트 층이 들어가면서 추천의 의미도 바뀌었습니다 — “비슷한 그림"에서 “이 축을 연습하는 데 맞는 참고물” 로. 한 끗 가이드는 이름도 골격도 프로토타입에서 나왔고, DraWe로 가면서 표현이 세분화되고 분석 데이터가 얹혔습니다.

artcoach에서 검증한 것 DraWe에서 더해진 구현
한 끗 가이드 — 분석 → 한 끗 포인트 → 레퍼런스 → 다음 단계 → 성장 흐름 같은 골격에 그림 위 ①② 오버레이 마커, “지금 바로 수정” 체크리스트, 추천 이유·태그 뱃지
성장 상태머신 — 목표 유지 · 반복 패턴 추적 · 단계 진행 판정 완성작 갤러리의 성장 로직 구현 — 성장 통계 · 반복 문제 TOP3 · 5단계 커리큘럼 프로그레스 · 주별 요청 추이
관찰(VLM) → 진단(taxonomy) → 검색 → 코칭 파이프라인 같은 역할 분리를 유지한 채 팀 서비스로 이식
가드레일 — 닫힌 세계 · 금지 표현 검사 환각 방지 게이트
회귀 테스트(소규모 손 라벨 · 합성 데이터) 골든셋 기반 정확도 평가 루프 — 실제 그림에 시스템 출력을 보기 전 블라인드 라벨을 달고, 축 정확도를 before/after로 재며 코드를 고침
벡터 스토어 어댑터(백엔드 중립) AI 모델 교체 가능 구조 — 프롬프트·골든셋·기대값을 고정한 채 백엔드만 스위치해 정확도·게이트·레이턴시·실패율·비용을 페어드 비교

마지막 두 행이 실제로 무엇을 바꿨는지가 중요합니다. 프로토타입으로 가이드를 테스트할 때는 가이드가 안 나오고 흰 화면이 뜨거나, 손 스케치를 올렸는데 명암 얘기가 돌아오는 일이 있었습니다. 눈으로 보고 “이상한데” 하고 넘어가는 수준이었죠. DraWe에서 라벨된 그림으로 1차 축 예측이 맞는지 회귀 테스트하기 시작하면서 그런 오분류가 줄었습니다. 검증 장치가 생기니 고칠 대상이 보였습니다.

오버레이 마커도 DraWe에서 처음 만들었습니다. 프로토타입에서는 말로만 짚었는데, 측정된 좌표가 이미 있으니 그림 위에 찍자는 판단이 팀 단계에서 나왔습니다.

반대로 옮기지 않은 것도 있습니다 — 평가를 통과 못 한 축들. 제품에는 근거를 댈 수 있는 것만 넣었습니다.

파이프라인과 설계 결정

업로드 → 안전 스크리닝 → 장면 분석(CLIP) · 포즈 추출 → 라우팅
      → 성장 컨텍스트 로드 → 진단(taxonomy 14축) → 레퍼런스 검색
      → 코칭 생성(LLM) → 가드레일 검증 → 로드맵 반영 → 응답

진단이 짚는 축은 이런 것들입니다. 축마다 구축선 도식을 직접 만들어 코퍼스에 넣었고, 진단 결과에 맞는 도식이 코칭과 함께 나갑니다.

① LLM은 결정자가 아니다

진단·목표 선정·반복 패턴 추적·단계 진행 판정은 전부 결정적(non-LLM) 로직이고, LLM은 코칭 문장 생성에만 씁니다. 가드레일이 스키마 · 닫힌 세계(주어진 축과 검색된 레퍼런스 밖으로 못 나감) · 금지 표현 · 근거 존재를 검증하고, 통과 못 한 문장은 사용자에게 나가지 않습니다.

문장 형식도 고정했습니다 — Observation → Effect → Experiment. “비율이 이상해요"는 관찰도 처방도 아니라, 사용자를 다시 검색 앞에 세워둘 뿐이니까요.

② “평가하지 않는다"와 “성장 로드맵"을 공존시키기

성장과 커리큘럼을 함께 보여주는 방향은 팀 논의와 교육 과정 멘토링을 거쳐 발전시킨 제품 방향입니다. 제 역할은 그 방향을 판정 가능한 규칙과 상태머신으로 구현하는 것이었습니다 — 축마다 new → practicing → improving → steady 상태를 두고, 목표 유지·반복 패턴 추적·단계 진행 판정을 전이 규칙으로 정의했습니다.

까다로운 건 점수·등급을 안 매기면서 로드맵은 갖고 있어야 한다는 충돌이었고, 해결은 불변식 하나였습니다.

내부 성장 단계와 레벨 추정은 절대 사용자에게 라벨로 노출되지 않는다. 하는 일은 둘뿐 — 첫 업로드 때 “어디서부터 같이 볼지"를 그림에서 고르고, 코칭 순서·톤의 내부 힌트가 된다.

실력을 판정하는 게 아니라 커리큘럼의 어느 지점에서 함께 보면 효과적인가만 정하는 것. 이 선은 금지 표현 검사로 강제했습니다. 진행 판정은 시간이 아니라 업로드 장수 기준입니다 — 일주일 동안 한 장도 안 그린 사람에게 “일주일 지났으니 다음 단계"는 의미가 없으니까요.

③ 확인 안 된 건 말하지 않는다

MediaPipe는 사진에만 동작합니다 — 스케치에서는 손 키포인트가 0개 검출됩니다. 그래서 키포인트 대신 VLM 관찰자를 만들었는데, 이건 관찰이지 측정이 아닙니다. 2회 호출 교차 일관성이 맞을 때만 신뢰도를 주고, 결과는 measured=False(관찰 = 가설)로 주입해 “측정 = 사실"을 오염시키지 않습니다.

중요한 건 못 쟀을 때의 동작입니다. 관찰이 어긋나면 빈 관찰로 폴백하고 그 축을 말하지 않습니다. 같은 규칙이 여러 층에 있습니다.

  • 포즈 추출 실패 → 피사체 마스크 폴백 → 전역 통계 → 그마저 없으면 값 주장 보류
  • measured=False인 축 → 그림 위에 표기하지 않음(오버레이 불변식)
  • 적용 가능한 축이 없음 → 단정 대신 가설형 안내
  • 근거 없음 → 가드레일이 문장을 막음

축을 늘리는 것보다 확인된 것만 말하는 상태가 이 시스템의 기본값입니다.

평가셋으로 검증한 뒤에 적용한다

“좋아진 것 같다"로는 팀 서비스에 넣을지 말지를 정할 수 없으니 축마다 평가셋을 만들고 통과한 것만 적용했습니다. 다만 여기서의 평가는 회귀 테스트 수준이었다는 걸 분명히 해둡니다 — safety(19)·retrieval(30)은 손으로 쓴 케이스고, 명암 축은 합성 결함을 주입해 측정기를 채점했습니다(피사체 마스크 도입 전 커버리지 0/32, 도입 후 32/32).

실제 그림에 라벨을 달아 정확도를 재는 건 DraWe에 가서야 갖췄습니다. 여기서는 “안 깨졌는가"를 봤고, 거기서는 “맞았는가"를 봤습니다.

손 관찰은 이 기준을 통과하지 못했습니다. 충실도 평가에 사람 라벨이 필요한데 그걸 만들지 못했고, 그래서 서비스에 넣지 않았습니다. 만들었는데 안 쓴 게 아니라 근거를 못 대서 안 쓴 것이고, DraWe에도 옮기지 않았습니다.

그 마스크 도입에서 배운 것 하나 — 계측 장치가 바뀌면 성장 비교가 오염됩니다. 측정 가능 영역을 바꾸는 변경은 정확도 개선이 아니라 자를 바꾸는 일이라, 연습 로그에 instrument_version을 박아 버전 경계에서 비교를 끊었습니다.

레퍼런스 코퍼스는 처음부터 상업적으로 사용 가능한 자료만 넣었습니다(CC0 · 자체 렌더 · QC 통과한 생성분). 검색 결과가 아니라 진단이 고른 연습 자료라서, 라이선스가 곧 서비스의 제약이 되니까요.

한계

자동 측정 신호는 기하·명도 통계 기반 휴리스틱이지 학습된 진단 모델이 아닙니다. taxonomy 14축 중 절반 가까이는 자동 측정이 없거나 보수적 임계값으로 묶여 있습니다. 정확도를 올리는 대신 측정이 부족할 때 무엇을 할지를 정해뒀고, 한 문장으로 하면 틀린 말을 하느니 덜 말하는 쪽입니다.
